# Issue #29 辞書ハッシュ修正レポート

## 結論

辞書JSONのハッシュを生バイトではなく正規化したJSON内容から計算するように変更しました。

修正後はLFとCRLFのどちらでも同じハッシュになり、JSONの値を変更した場合は従来どおりmanifest不一致として拒否します。

Issue #28と同じ動画、ROI、解析設定による全体解析では、回避操作なしでOCR成功211件の翻訳がすべて完了しました。

処理状態は`completed_with_errors`ですが、44件のエラーはOCR失敗に対応しており、辞書検証または翻訳事前確認のエラーはありません。

## 原因

修正前のmanifestは、管理対象の大半についてWindows作業ツリーのCRLFバイト列から計算したSHA-256を保持していました。

一方、`sources.json`は辞書拡充後のmanifest更新が漏れており、manifest、Git blob、Windows作業ツリーの三つが異なる値でした。

| 対象 | SHA-256 |
| --- | --- |
| 修正前manifestの`sources.json` | `f56a7cf639a3fe6ab9f363eb583b73792b62065c2073c4b6a49e86c161684b3d` |
| Git blobの`sources.json` | `d2c3b8db6c1bac36359e249ca0fcd6144ffb7750d14f44b070fc9428d5704093` |
| Windows作業ツリーの`sources.json` | `2468c298df0264656ec3ca3a63cfce05be8bb6c27bd8b4b89f718510df2c889e` |

Git blobの時点でmanifestと一致しないため、直接の停止原因にはmanifest更新漏れが含まれます。

ほかの管理対象はWindows作業ツリーでは一致しましたが、Git blobのLF版とは一致しませんでした。

したがって、生バイト方式を維持してmanifest値だけを更新しても、異なる改行設定や配布工程で再発します。

## 修正したハッシュ方式

manifest schemaを3へ更新し、`hash_algorithm`へ`sha256-canonical-json-v1`を記録しました。

この方式はJSONを読み込み、オブジェクトのキーを並べ替え、不要な空白を除いたUTF-8表現へ変換してからSHA-256を計算します。

LF、CRLF、インデント、末尾改行の違いはハッシュへ影響しません。

文字列、数値、真偽値、null、配列の内容または配列順を変えるとハッシュが変わります。

実行時ローダーとmanifest更新処理は同じ実装を使用するため、生成側と検証側で計算方法が分岐しません。

過去コミットの辞書を比較する開発用処理も、読み込んだ旧manifestを一時領域でschema 3へ変換してから同じ方式で検証します。

## 配布対象

新しいハッシュ処理をTauriの配布リソースへ追加しました。

MSIとNSISの配布ビルドを作成し、生成先へコピーされたmanifest、辞書JSON、ハッシュ処理を使って辞書を読み込みました。

配布リソースから、辞書版`lol-ko-ja-app-16.18.1-2026-09-27`と109件の別名を読み込めることを確認しました。

インストーラー自体のインストール操作は行っていません。

## 回帰テスト

次の条件を自動テストへ追加しました。

- 同じJSON内容をLF、CRLF、異なるインデントで保存しても同じハッシュになる。
- JSONの意味内容を変更するとmanifest不一致で拒否される。
- 辞書更新後にmanifestを再生成すると新しいハッシュになり、辞書を読み込める。
- LF版とCRLF版の全管理対象ファイルを同じmanifestで読み込める。
- manifestが参照する全辞書ファイルとハッシュ処理がTauriの配布対象に含まれる。

## 対象外

Issue #30のHUD誤検出、OCR精度、翻訳品質、辞書語彙は変更していません。

この修正は辞書の完全性検証を無効化せず、JSONの意味内容に対する検証へ変更したものです。
